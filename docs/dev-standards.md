# 開發規範（通用版）

這份是 Sam 所有專案共用的開發規範，原檔在專案資料夾的 `standards/CLAUDE.md`，可以放在 `~/.claude/CLAUDE.md` 套用到所有專案。這裡留一份，讓雲端工作階段（讀不到使用者層級設定）也能讀到。
專案自己的 `CLAUDE.md` 會寫該專案的技術細節，兩者衝突時以專案的為準。

標示說明：
- 【Sam】：我明確提出過的要求。
- 【慣例】：先前合作時採用、我審過並合併的做法。
- 【通用】：業界常見的 Clean Code / SOLID 原則，補充用。

---

## 1. 溝通與工作流程

- 【Sam】我說「先純討論」時，只分析、不改程式、不開 PR，等我說要做再動手。
- 【Sam】大一點的改動（改名、換服務、加大功能、上架 App 等）先評估：修改幅度、要動到哪些檔案、成本（含每月營運費用）、風險，再讓我決定。
- 【Sam】技術分析（效能、擴展、監控、壓力測試、資安）請以業界標準來評估，並說明依據。
- 【Sam】新功能要先能在 staging（測試環境）試用，我確認後才發佈到 production。新專案也要規劃 staging 與 production 分開，測試資料不要進正式環境。
- 【Sam】PR 由我審；我回「LGTM」或「請合併」之前不要合併。
- 【Sam】新增功能時，不要違背產品最初的定位與承諾（例如「不用註冊就能用」這類核心特點），有衝突要先講。
- 【慣例】需要我做選擇時，列出選項並標出推薦，讓我直接回題號。
- 【慣例】回覆用繁體中文，先講結論或要我做的事。

## 2. 程式碼品質：Clean Code

- 【Sam】程式要依照 Clean Code 的標準撰寫；為了加功能而犧牲整潔度的地方，要當作技術債處理。
- 【Sam】在規模還小的時候就定期盤點技術債，不要等變大才整理。
- 【通用】命名要能說明用途，不用縮寫或謎樣的單字母變數（迴圈索引除外）。
- 【通用】函式只做一件事、保持短小；參數盡量少，超過三個考慮包成物件。
- 【通用】不要重複（DRY）：同樣的邏輯、常數、資料路徑只寫在一個地方。
- 【通用】魔術數字與限制值集中成具名常數。
- 【通用】註解寫「為什麼」，不寫「做了什麼」；程式本身應該能說明做了什麼。
- 【通用】錯誤要明確處理並給使用者看得懂的訊息，不要默默吞掉。
- 【通用】避免巨大的全域可變狀態（God object）；狀態有明確的擁有者。
- 【通用】刪掉死碼與不再使用的功能，不要註解掉留著。

## 3. 設計：物件導向與 SOLID

- 【Sam】適合用物件導向設計的地方就用類別封裝，並依照 SOLID 原則設計與重構。
- 【通用】**S（單一職責）**：一個模組或類別只有一個改變的理由。不要一個檔案做所有事，依功能拆模組。
- 【通用】**O（開放封閉）**：新增一種東西（例如新的訊息種類、付款方式）應該是「加一個條目」，而不是在十幾個地方加 `if / else`。用註冊表（registry）或多型取代分散的條件分支。
- 【通用】**L（里氏替換）**：子類別或替代實作要能完全替換原本的，不改變呼叫端預期的行為。
- 【通用】**I（介面隔離）**：介面小而專一，呼叫端不必依賴用不到的方法。
- 【通用】**D（依賴反轉）**：畫面與商業邏輯依賴抽象，不直接綁死資料庫或外部服務。所有寫入集中在一層 API／資料層，畫面不自己組資料路徑去寫資料庫；只有一個地方負責載入外部 SDK。
- 【慣例】資料層用事件（emitter／訂閱）通知畫面更新，而不是資料層直接呼叫畫面函式。

## 4. 重構與測試

- 【慣例】重構前先補測試當安全網（端到端測試鎖住現有行為），重構後同一批測試要全部通過。
- 【慣例】重構 PR 不改任何功能；功能變更和重構分開成不同 PR。
- 【慣例】純函式補單元測試；權限或資料庫規則要有規則測試。
- 【慣例】開 PR 前本機測試全綠，PR 上 CI 也要全綠，失敗要先查清楚原因再修，不要跳過或停用測試。
- 【通用】修 bug 時先寫一個能重現問題的測試，再修到它通過。

## 5. 介面與文案

- 【Sam】介面要專業、精緻、一致（我曾要求用設計文章的原則，例如完形心理學 Gestalt 原則，來檢視整體介面）。
- 【慣例】改到畫面的 PR 附上截圖；有深色模式的專案，亮色和暗色都附。
- 【慣例】多語系專案：每種語言的字串 key 數量要一致，新增文字要同時補齊所有語言。
- 【通用】注意無障礙：文字對比度符合 WCAG，按鈕要有可讀的標籤。

## 6. Git 與 PR

- 【慣例】一個 PR 一個主題；多項要求可以拆成多個 commit，一項一個。
- 【慣例】PR 說明寫清楚：改了什麼、為什麼、怎麼測、有沒有需要我決定或手動設定的事。
- 【通用】密鑰、API 私密金鑰、服務帳戶 JSON 不進版本庫，放在 CI secrets 或環境變數。
- 【通用】產生出來的檔案（例如由腳本產生的設定）要標明來源，CI 檢查兩者一致。
